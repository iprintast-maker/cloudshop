# Айпринт: заказы, чеки, редактирование и отчёты

Изменения предназначены только для `iprintast-maker/cloudshop` и базы `cvlwoylsdgvwycntyqxu`. Конфигурация проекта не менялась. Полароид и другие клиентские сайты не обновлялись.

## Что меняется на сайте

- Раздел отложенных производственных заказов называется «Заказы в работе». Товарные чеки и напоминание о кассовом чеке — отдельные функции.
- Товарный чек скачивается непосредственно в PDF с логотипом, позициями, скидкой, списанием баллов, итогом и оплатой; `window.print` не вызывается.
- Допродажа появляется на 6,5 секунды как немодальная подсказка без подтверждения. Корзина не меняется.
- У числовых полей нет стрелок; колесо и клавиши стрелок не меняют сфокусированное значение.

## Обновление базы

Для функций ниже нужно применить `supabase/migrations/20261120_iprint_sales_workflow.sql`, затем `supabase/migrations/20261120_iprint_admin_report_sync.sql` **только к Айпринту**. Файлы `bootstrap` повторно запускать на рабочей базе нельзя.

В Supabase откройте проект `cvlwoylsdgvwycntyqxu` → SQL Editor → New query. Выполните содержимое одного нового SQL-файла. После успешного выполнения обновите сайт. Секретные ключи в браузерную конфигурацию или переписку не нужны.

До применения миграции обычное оформление продаж остаётся на прежних функциях. Зависимые новые элементы скрыты до ответа `iprint_workflow_info`; прямое скачивание PDF, название раздела, подсказки и ввод количества работают отдельно. Это позволяет опубликовать безопасную часть до выдачи доступа к базе.

После применения миграции:

- В продаже появляется «Кассовый чек выдан», по умолчанию без галочки. Это напоминание сотруднику; фискализации нет. В истории выданный чек обозначен ✅, невыданный — пустая ячейка. Есть кнопка «Чек выдан» и изменение галочки в окне продажи. Старые продажи не получают выдуманную отметку.
- Новые продажи и офлайн-очередь сохраняют отметку атомарно. Повтор синхронизации не перезаписывает более позднюю ручную отметку. Оплата заказа «при получении» также передаёт отметку.
- По нажатию на строку продажи открывается редактор. Любой активный сотрудник текущего филиала может менять действующие продажи за сегодня, независимо от автора. Администратор может работать без открытой смены. Номер, дата и первоначальный кассир сохраняются. Прошлые, удалённые и возвращённые продажи доступны только для просмотра.
- Меняются позиции, варианты, количества, цены, скидка, списание баллов, оплата, комментарий и отметка чека. Обновление транзакционное, с версией для защиты от одновременных правок. Склад и долги пересчитываются; старые списания и состояния продажи сохраняются в закрытом аудите. Баллы корректируются разницей, без увеличения числа покупок. Связь с клиентом клубной карты сохраняется. Изменение уже погашенной суммы долга блокируется: старая модель не поддерживает частично оплаченный долг.
- Если день уже перенесён автоматически, исправленная продажа обновляет его суммы; ручной отчёт автоматически не перезаписывается.
- Перед переносом проверяется наличие листа филиала, месяца и строки даты. Недостающие создаются; существующие данные сохраняются. Общий лист «Выручка» без филиала используется только при одном действующем реальном филиале. В остальных случаях создаётся отдельный лист. Повреждённый существующий месяц с пропавшей датой не переписывается автоматически, ошибка показывается сотруднику.

## Проверки

`NODE_PATH=<каталог зависимостей> node tests/sales-workflow-db.cjs`: локальный PostgreSQL PGlite 0.3.14, исходная схема/функции Айпринта; проверяет атомарность, чужого автора, версию, склад, баллы/долги, отчёт, добавление месяца, права и откат некорректной правки. Только тестовая база в памяти, без клиентских данных.

`NODE_PATH=<каталог зависимостей> node tests/sales-workflow-browser.cjs`: Playwright 1.58.2 и Chromium, локальный сервер на 8796, перехваченные ответы БД; проверяет PDF, напоминание, очередь, редактор, допродажу и колесо. Полученный PDF дополнительно проверяется `pdfinfo`.

`node build.mjs`: публикуются только файлы из `dist`, SQL/тесты в сайт не попадают.

Проверка на локальной схеме не подтверждает состояние рабочей базы или фактическую причину текущего сбоя отчётов. До доступа к клиентскому проекту и применения миграции эти пункты нельзя считать установленными и проверенными в рабочем Айпринте.

## Личный кассир на общей смене — 21.11.2026

Кассир рабочего места определяется по `staff_accounts.person_id` текущего личного логина и активному участнику общей смены. Порядок подключения сотрудников значения не имеет. При открытии каждой продажи показывается единственный кассир этого аккаунта; ручной выбор больше не запрашивается. При подключении к открытой смене первым выбран сам сотрудник, остальные участники и главный по ретуши сохраняются.

Смена аккаунта очищает прежнее рабочее место и незавершённую корзину. Перед сохранением и при восстановлении без связи проверяется соответствие кассира аккаунту; чужая сохранённая сессия не используется. Уже созданные офлайн-продажи сохраняют того кассира, который оформлял их первоначально. Непривязанный логин или сотрудник вне состава смены получает объяснение вместо подстановки первого участника. Новые логины нужно связывать с карточкой сотрудника в разделе «Логины».

Проверки: `tests/cashier-identity.cjs` (linkedom 0.18.12) и `tests/cashier-browser.cjs` (Playwright 1.58.2 + Chromium). Три изолированных рабочих места, одна смена, повторные продажи, смена аккаунта, неподключённый/неактивный сотрудник и защита офлайн-восстановления. Миграция базы для этого изменения не требуется: привязки существующих логинов Айпринта уже заполнены.
